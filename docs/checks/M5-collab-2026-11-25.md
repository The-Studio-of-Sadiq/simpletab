# M5 checkpoint: `npm run e2e:collab` (2026-11-25)

Test: `tools/e2e/collab.test.ts`. Result: **pass**.

## Setup

- Tournament: the benchmark generator's WUDC size (400 teams, 500 adjudicators, 100 rooms, five rounds played), plus 300 feedback records with a secret comment.
- One host and 15 staff devices, each a full `HostServiceImpl` in device mode, all on real TLS connections over 127.0.0.1:
  - 3 tab directors
  - 3 adjudication core
  - 2 Equity
  - 5 tab assistants
  - 2 display
- All 16 services ran in one Node process on one laptop: 11th Gen Intel Core i7-1165G7 (8 threads), 16 GB, Node 24.21.0. That is stricter than a real tab room, where each device does its own work on its own laptop.
- 40 team renames, saved in turn by the host, the tab directors and the tab assistants.

## Results

| Check | Result |
|---|---|
| Change saved → all 15 devices have it | p50 377 ms, **p95 451 ms**, max 480 ms (limit: p95 ≤ 1 s) |
| Pairing all 15 devices (code, six words, approval, first snapshot) | 25.9 s in total |
| Equity devices hold no feedback: no records, no comment text, no `feedback:` version keys | pass (tab directors hold all 300) |
| Promotion keeps every broadcast op | pass: the promoted chain starts with all 55 of the old host's entry hashes, then `host.promote`, as host 2 |
| The old host steps down when a device that knows host 2 reaches it | pass: read-only, and saves are refused |

## Where the time goes

Almost all of each delta's time is the host computing every role's view of a 400-team tournament (`project`) and diffing it against the previous one. The network adds little on one machine. Faster projections (incremental per record) would cut this if bigger tournaments need it; at WUDC size the limit is met with about half a second to spare.
